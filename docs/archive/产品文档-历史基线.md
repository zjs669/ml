# 玄枢 · 国学研习台

## 传统术数排盘、知识技能库与 AI 解读的一体化 Web 产品

产品需求 + 技术架构 + MySQL 数据设计 + AI 知识工程 + 商业化与合规方案

> 版本：V1.0  |  文档日期：2026-10-24  |  目标形态：先做网页版 MVP

> **项目原则：** 本项目定位为传统文化学习、术数排盘与资料研习工具。排盘引擎应当可复核，AI 负责解释与检索，不把模型当作历法或术数规则的唯一计算器。

---

# 0. 执行摘要

先做一个边界清晰、成本可控的网页版，不追求第一版“所有术数都能算、AI 自动学会一切”。建议项目名为“玄枢国学研习台”，对外表达为“传统术数资料、排盘与研习助手”，面向国学爱好者、术数初学者与有学习/整理需求的研习者。

首版应当先把确定性部分做好：四柱八字基础排盘、十神/藏干/五行、刑冲合害关系解释、排盘口径说明、历史记录；AI 只根据结构化排盘结果和经过审核的技能库生成解读。紫微斗数、六爻、奇门遁甲逐个接入，不能让大模型凭语言直觉去“心算排盘”。

建议技术组合：Vue 3 + TypeScript + Vite 前端；Python FastAPI 后端；MySQL 8 保存用户、排盘、知识库元数据、订单和用量记录；Redis 作为第二阶段的缓存/限流组件；LLM 用可替换的 Provider Adapter 接入。模型先用你有权使用的免费 API/平台配额测试，正式上线前必须确认商用条款、额度和数据规则。

最值得收费的并不是“预测一定准确”，而是：更可靠的排盘、可切换的流派口径、古籍/规则出处、结构化报告、命盘归档、对比研习与批量整理。不要承诺改命、保证婚姻/财富结果，也不要把产品设计为彩票、赌球、投机交易的预测工具。

首版成败指标：用户能否不看教程完成排盘；常见边界日期能否按公开口径复核；AI 解读能否引用技能库且不编造盘面；是否有真实用户愿意为省时、可追溯的研究体验付费。

# 1. 市场参考与竞品拆解

以下根据公开网页的产品介绍与可见价格页面整理，属于产品观察快照，不等于第三方审计，也不能证明对方真实收入。上线前应再次访问竞品网站，检查其最新功能、许可与价格。

## 1.1 参考对象

- 鲲侯 · 星河易道（xuebz.com）：公开首页把免费八字、紫微、奇门与择吉入口放在一起，周边还有文章、课程、直播、档案中心及业务套餐。可借鉴“工具 + 内容 + 用户档案 + 服务”的产品矩阵；不要第一天就做全站内容平台。
- 玄学 AI 会员（xuanxueai.com.cn）：公开会员页呈现免费体验、月付/年付、五术工具、AI 深度解读、古籍出处和专属服务。可借鉴“免费入口建立习惯，进阶解读收费”；页面上出现的 ¥88/月、¥880/年仅作竞品快照，不是本项目定价结论。
- 6yao.ai：公开首页围绕“提出一件事—起卦—查看盘面与解释依据—回看问题”，强调免费基础体验、历史报告和用户问题隐私。可借鉴清晰任务流程与报告回看；不要引导用户把卦象当作他人真实想法或确定结果。
- 紫微斗数排盘工具（如 18888.net.cn、tool.shixingji.club/work/ziwei、9zi.ai 等公开页面）：强调十二宫、星曜、四化、大限流年、真太阳时、排盘口径与本地计算。可借鉴参数显式化、流派口径公开和隐私友好的本地计算。

## 1.2 竞品功能矩阵

| 维度 | 常见做法 | 本项目建议 |
| --- | --- | --- |
| 流量入口 | 免费排盘、每日工具、百科文章 | 先上四柱排盘 + 刑冲合害说明 + 免费术语百科 |
| 付费点 | 深度解读、会员、报告、档案/专业工具 | 先卖单次报告和月度额度，后做专业版 |
| 信任机制 | 标出派别、真太阳时、古籍出处或计算口径 | 每张盘显示算法版本、时间口径、规则来源和不确定项 |
| 用户留存 | 历史命盘、分享链接、每日内容、研习资料 | 命盘档案、笔记、收藏规则、前后版本对比 |
| AI 价值 | 按问题生成长文解读 | 输出带引用的结构化报告，区分“盘面事实”与“传统解释” |
| 隐私设计 | 部分产品主打浏览器本地计算 | 未登录可在前端计算基础盘；需 AI 解读/保存时才明确告知并请求必要数据 |

## 1.3 我们的差异化

- 口径透明：同一套命盘允许选择“本工具采用的年界、换日规则、节气规则”等口径，并在报告中记录。
- 计算和解读分离：程序给出干支、宫位、爻位等结构化事实；AI 只能解释这些事实，不能偷偷重算或改写输入。
- 出处可追溯：每个关键解释尽可能关联到已审核的知识片段、书目、章节或自建规则编号。若找不到依据，必须明确说“知识库暂无依据”。
- 技能库可维护：某个流派规则变更只发布新的技能版本，不必重写整个系统或重新训练基础模型。
- 商业路径轻：先卖文本报告与学习工具，不做 AI 漫剧、不买大批视频素材、不依赖图像生成。

# 2. 产品定位、客群与边界

## 2.1 目标用户

- 国学/术数学习者：需要查术语、比较不同口径、保存命盘和学习笔记。
- 内容创作者：需要把四柱、紫微、六爻等术语整理成结构化知识卡或文章初稿，再由本人审校。
- 传统文化研究者：需要可检索的古籍引用、出处索引、版本说明和规则对照。
- 专业研习者（后续）：需要客户档案与报告模板；上线前要特别关注个人信息保护、服务范围、专业责任与所在地区监管要求。

## 2.2 产品承诺

“帮助用户学习和整理传统术数资料，并根据可复核的排盘数据生成带依据的文化解读。” 不承诺科学预测能力，不宣称能决定人的命运，不用恐吓、焦虑或限时话术诱导购买。

## 2.3 明确不做的功能

- 不开发彩票、赌博、下注、赌球、博彩或投机交易的预测、推荐和自动化策略。
- 不输出医疗诊断、停药建议、法律判断、投资买卖建议，或以命盘替代现实专业意见。
- 不做“保证复合/保证发财/保证改命/灾祸倒计时”等确定性承诺。
- 不通过用户问题自动判断现实中的第三方内心、忠诚度或隐私事实。
- 不收集与功能无关的真实姓名、身份证号码、精确地址、通讯录等数据；出生资料默认尽量不保存。

# 3. MVP 范围与版本路线

## 3.1 第一版（MVP，先形成闭环）

- 首页、注册/登录、术数工具目录、FAQ 与说明页。
- 四柱八字基础排盘：公历输入、出生时刻、可选出生地/时区、性别字段（只在所选算法确有需要时收集）、历法口径提示。
- 基础命盘展示：四柱干支、藏干、十神、五行统计、基础大运（需明确起运规则和误差边界）。
- 刑、冲、合、害、破等关系引擎：先给出“哪些关系被规则触发”，不直接让模型推断。
- AI 解释：性格/学习/传统文化研读等低风险方向；每个关键段落尽量挂知识引用；可选择简版/详版。
- 命盘保存、笔记、收藏、复制/导出为文本；删除账号/记录入口。
- 每日免费额度、一次性报告订单、会员用量额度的最小实现。

## 3.2 第二阶段

- 紫微斗数排盘：十二宫、主辅星、四化、大限/流年，明确安星法与流派口径。
- 六爻：起卦方式、动爻、变卦、六亲/六神/地支等结构化规则。
- 知识库搜索：古籍概念、规则条目、术语词典与相互引用。
- 专业报告导出、分享链接的脱敏预览、知识卡片生成。

## 3.3 第三阶段

- 奇门遁甲排盘：先冻结一个可说明的排盘口径，再实现局数、阴阳遁、九宫、门星神等。
- 多盘对照、不同流派差异分析、批量资料导入、研习者工作台。
- 训练数据集版本、自动回归评测、运营后台的审核工作流。

阶段原则：模块数量不是竞争力。每上一个术数模块，必须同时有排盘口径说明、至少一组独立核对样例、错误处理、知识来源和安全边界。

# 4. 页面信息架构与关键流程

## 4.1 页面清单

- / 首页：项目介绍、免费四柱排盘入口、文化百科、最近更新、免责声明。
- /tools：工具目录；每个模块标注“已上线 / 测试中 / 计划中”，不展示不可用的假按钮。
- /bazi：四柱排盘表单与计算结果；显示口径信息和复制/保存入口。
- /charts/:id：命盘详情、关系图、AI 解读、笔记、算法版本。
- /knowledge：术语检索、古籍/规则出处、相关词条。
- /pricing：免费版、单次报告、会员权益、额度消耗规则、退款说明。
- /account：个人资料、记录管理、导出/删除、用量和订单。
- /admin：知识审核、技能版本、AI 调用日志、异常反馈、订单和用户支持。

## 4.2 用户流程

访客 → 选择工具 → 填写最少必要信息 → 前端校验 → 后端计算并返回结构化盘面 → 用户查看免费盘面 → 选择 AI 解读（显示将使用哪些数据）→ 后端检索知识库 → LLM 按固定 JSON Schema 生成解释 → 输出校验/安全检查 → 保存报告（用户主动选择）→ 免费额度或付费权益扣减。

## 4.3 关键交互要求

- 输入时间不完整时必须允许“未知/不确定”，并在结果中标注影响，不擅自补成精确时刻。
- 出生城市用于真太阳时换算时，应展示城市、时区、经纬度来源和换算结果；默认不存储精确定位。
- 盘面必须显示“排盘算法版本”和“解读生成时间”；修改排盘口径后，旧报告不能静默覆盖。
- 用户点击保存、分享、付费之前，清楚展示保存的数据项、分享范围、报告内容与额度消耗。
- 分享链接默认私密、随机不可猜，并提供失效时间/撤销按钮。

# 5. 技术架构（建议实现）

## 5.1 技术栈

- 前端：Vue 3 + TypeScript + Vite；UI 可选 Element Plus 或 Naive UI；状态管理 Pinia；请求层统一封装 Axios/fetch。
- 后端：Python 3.12 + FastAPI；Pydantic 做入参/出参校验；SQLAlchemy 2 + Alembic 管理数据库模型与迁移。
- 数据库：MySQL 8.0/8.4，utf8mb4；所有时间统一以 UTC 存储，展示时按用户时区转换。
- 缓存/限流：MVP 可不用 Redis；用户变多后增加 Redis 存短期验证码、限流计数、任务状态与缓存。
- AI：统一 LLM Provider 接口，支持 OpenAI-compatible HTTP API；模型名、Base URL、超时、并发上限均从环境变量读取。
- 部署：Linux + Docker Compose + Nginx + HTTPS；日志写标准输出并配置轮转；数据库定期备份。

# 6. 排盘模块设计：程序算事实，AI 做解释

## 6.1 四柱八字

- 输入：公历或农历日期（首版推荐只支持公历，农历转换经充分测试后再开放）、时分、出生时区、出生地（可选）、时辰不详标记、排盘口径。
- 输出：年柱、月柱、日柱、时柱；天干地支；藏干；十神；五行计数；节气边界说明；如有大运则包括起运算法与结果。
- 边界规则：立春前后、节气交接时刻、23:00 子时换日、闰月/历法换算、夏令时/历史时区、未知时刻均须做单元测试。
- 算法来源：优先采用经过审查、许可兼容且可维护的日期/历法库；不要在商业产品中直接复制来源不明的代码。
- 结果元数据：algorithm_name、algorithm_version、time_zone、solar_time_method、year_boundary_rule、day_boundary_rule、ephemeris_version。

## 6.2 刑冲合害与十神关系引擎

- 把关系拆成明确规则，不让 LLM 自行列举。示例规则类别：地支六合、三合、三会、六冲、相刑、相害、相破；天干五合/冲（仅在选定体系确有定义时）；十神、藏干、旺衰等。
- 每条规则建议存：rule_id、体系、输入条件、输出关系、优先级、例外、来源、版本、生效状态。
- 多条关系同时存在时只展示“触发了哪些规则”，不由程序直接输出灾祸式结论。
- 解读要把“关系事实”“传统流派解释”“现实可验证建议”分段，避免把一个符号直接说成确定事件。

## 6.3 紫微斗数

- 先选定一套具体安星法/四化口径作为默认配置，并在高级设置中标明；不可把不同流派算法混拼成一个所谓唯一正确结果。
- 输出结构包含十二宫、宫干、主星/辅星/煞星、四化、大限、流年，以及每一项的来源口径。
- 可评估 iztro 等开源排盘引擎，但在采用前必须阅读并遵守当前许可证，核对依赖、归属声明、商用与再分发条件；文档不替代许可证审查。
- MVP 不需要用模型“训练紫微排盘”。先集成确定性引擎和参考命例，AI 只在结构化命盘上做解释。

## 6.4 六爻

- 输入：起卦方式（手动六次、数字/时间等应清晰标识）、起卦时间、问题类别（不要提供赌博/下注类别）、排盘口径。
- 输出：本卦、动爻、变卦、世应、六亲、六神、地支五行等，以选定规则为准。
- 起卦随机性与排盘确定性分开：起卦值一旦确定，排盘结果应可重复。记录随机来源或用户输入，但不要宣称随机结果具有客观预测效力。
- 问题输入要有安全提示；针对健康、法律、金融、博彩、威胁/控制他人等主题，限制或改为通用的现实信息建议。

## 6.5 奇门遁甲

- 先只支持一个明确的排盘口径，并说明所用历法、局数起法、阴阳遁、值符/值使、九宫配置规则。
- 使用可测试的规则模块，不能把“AI 解释的盘面”反向当作权威计算结果。
- 开发顺序建议放在四柱与紫微之后；奇门规则分支复杂，口径含糊会造成后续大量争议和返工。

## 6.6 通用引擎接口

各术数模块统一遵循 ChartEngine 接口，例如 calculate(input, convention) -> ChartResult。ChartResult 至少包含：domain、input_summary、chart_facts、triggered_rules、convention、algorithm_version、warnings、source_refs。任何模块不直接拼接 AI 文案。

# 7. AI 技能库：把“会算、会讲、会引用”拆开

## 7.1 “技能库”是什么

这里的技能库不等于训练一个全新大模型。它是一套版本化的领域规则、提示词、工具调用定义、术语词典、知识来源、样例输入输出和自动评测集。模型在回答前，根据模块和问题检索适用技能；确定性计算仍由程序完成。

## 7.2 技能包建议字段

- skill_id：稳定唯一编号，例如 bazi.relations.clash.v1。
- domain：bazi / ziwei / liuyao / qimen / general。
- title、description、version、status：标题、用途、版本、草稿/审核中/发布/弃用。
- preconditions：何种排盘口径、哪些输入字段齐全时才能使用。
- rule_spec：机器可读的判断条件或解释结构，不要把全部规则藏在长提示词里。
- prompt_template：模型要做的解释任务、禁止事项、输出格式。
- source_refs：书名、版本、章节/页码或授权知识库条目。
- examples：经过审核的正例、边界例、反例。
- eval_cases：自动回归测试输入与预期结果。
- safety_policy：禁止用途、需要拒答或降级响应的主题。

## 7.3 自动化知识处理流水线

原始资料（仅限已授权或允许使用的文本） → 格式提取 → 去重/清洗 → 章节切分 → 元数据标注 → 术语识别 → 规则/出处抽取 → 自动生成候选问答 → 版权/引用/敏感内容检查 → 自动评测 → 人工抽查/审核 → 发布到检索库 → 版本留档 → 上线后监控反馈。

“全自动”应理解为自动处理和自动测试，不是让模型自行从用户对话中学到新结论并自动发布。没有人工审核门槛，错误解释可能持续放大，知识库也容易被恶意输入污染。

## 7.4 资料来源和版权

- 优先使用公版古籍、明确开放许可的电子文本、你自己撰写的规则摘要、取得授权的课程/文章。
- 公版原文不代表现代整理版、注释、排版、翻译和电子数据库都无版权限制；保留来源、版本、许可和使用范围。
- 不要批量抓取竞品会员内容、付费课程或受版权保护的电子书，不要将未经许可的资料上传到第三方模型。
- 每个片段必须带 source_id、source_title、edition、license_status、chapter/page、retrieved_at 与 content_hash。

## 7.5 自动训练路线图

- 第 1 步：RAG 检索增强生成。把术语、规则和古籍片段放进可搜索知识库，生成时引用来源。这是首选。
- 第 2 步：工具调用。模型只能请求 bazi.calculate、relation.lookup、ziwei.calculate 等工具；工具返回确定性 JSON 后模型再解释。
- 第 3 步：自动评测。对固定命例执行回归测试，比较盘面、引用、结构、风险提示和成本。
- 第 4 步：专家审核后构建 SFT 数据集。只使用有权训练的数据、人工审定的输入/输出对；先小规模评测，不因训练而假设准确率必然提升。
- 第 5 步：谨慎考虑微调。仅当提示词 + RAG + 工具调用已稳定但仍出现明确、可复现的格式/风格问题时，再评估微调。微调不应该替代排盘算法或知识来源。

## 7.6 禁止的“自动学习”模式

- 不将所有用户输入直接写进训练集；用户输入可能包含个人隐私、错误命例或提示注入。
- 不使用付费模型的输出未经许可反向训练另一个模型；先核对 API 服务条款。
- 不让 AI 自动改写生产环境的规则表；更改必须经过版本发布、回归测试和回滚方案。
- 不把用户点赞当作事实正确性标签；反馈只作为待审查信号。

# 9. REST API 设计

统一前缀 /api/v1；用 HTTP 状态码表达错误；所有写请求需要鉴权并做权限检查；对报告生成、支付回调使用幂等键。

- POST /auth/register：创建账号（如开放注册；可改为邮箱验证码）。
- POST /auth/login：登录并获取会话/JWT；刷新令牌要有有效期、撤销和安全存储策略。
- POST /charts/bazi/calculate：四柱排盘计算；默认只返回结果，不自动保存。
- POST /charts/{chart_id}/reports：基于已保存命盘生成 AI 报告。
- GET /charts：列出当前用户的命盘；分页返回，永远不能通过修改 ID 读取他人记录。
- DELETE /charts/{chart_id}：删除个人命盘及关联报告（按保留规则处理必要订单记录）。
- GET /knowledge/search?q=...&domain=bazi：检索已审核的公开知识条目。
- GET /billing/plans：返回当前可购买套餐及权益。
- POST /billing/orders：创建待支付订单。
- POST /billing/webhooks/{provider}：支付回调，必须校验签名和金额，并幂等处理。
- GET /me/usage：查看免费额度、付费额度和消费记录。
- POST /feedback：提交评分/错误报告。

3. 区分【盘面事实】【传统解释】【现实中的可验证建议】。
4. 不把命理描述为科学诊断或必然预言，不恐吓用户，不给彩票/下注/博彩建议。

## 10.4 输出 JSON Schema 建议

summary: string；observations: array[{fact, rule_ids}]；traditional_interpretations: array[{claim, tradition, citation_ids, confidence_note}]；practical_reflections: array[string]；citations: array[{chunk_id, title, location}]；uncertainties: array[string]；safety_note: string。服务器端要校验 JSON 结构、引用 ID 是否真实存在、是否出现禁止内容或盘面事实不一致；校验失败时进行一次受控重试，仍失败则返回降级结果。

# 11. 付费和商业化设计

## 11.1 付费梯度（先当作实验假设）

- 免费版：基础排盘、基础术语、每日少量 AI 解读；可不登录查看基础盘面，注册只用于保存记录。
- 单次报告：例如 ¥9.9–19.9 的初始测试区间，包含指定主题的结构化报告、规则引用和下载；价格只用于验证，不是行业标准。
- 月度会员：例如 ¥29–49/月测试；包含更高的报告额度、保存/对比、模板和知识库进阶检索。
- 研习者/创作者版：后续根据真实使用价值增加批量命盘、报告模板、笔记导出或团队空间；不要在用户很少时先做复杂企业套餐。
- 定价参考：部分公开竞品页面显示过约 ¥88/月或 ¥880/年等会员标价；这些页面是竞品观察，不说明市场愿意为你的产品支付同样价格。

## 11.2 为什么用户会付费

- 不是“AI 比别人神”，而是“少花时间、步骤完整、来源可查、记录能复用”。
- 报告差异必须可见：排盘口径、触发规则、引用出处、不同流派对比、导出体验。
- 免费内容要能独立满足基础需求，不用恐吓、虚假倒计时或隐瞒续费规则把人推向付费。
- 先从用户愿意付费的一件事切入，例如“可核对的四柱报告 + 术语解释”，不要同时开发几十个模块。

## 11.3 收入模型（公式，不是预测）

```text
月收入 ≈ 付费用户数 × 月均实收；贡献毛利 ≈ 实收 − 模型 API 成本 − 支付手续费 − 退款损耗 − 必要运维成本。
举例：100 名活跃用户里有 5 人购买 ¥29 的月度权益，则本月会员收入为 ¥145（未扣任何成本）。这只是算术示例，不代表可实现的转化率或收入。
```

## 11.4 成本控制

- 排盘计算尽量用本地确定性代码，不消耗 LLM Token。
- 同一盘面的“基础说明”可缓存；个性化报告才调用模型。缓存必须按口径版本、prompt 版本、knowledge version 区分。
- 限制单次最大输出、每用户每日额度、并发数和异常重试；避免循环调用造成账单失控。
- 用量账本要按“先预扣/锁额—调用模型—按实际结果结算—失败退款额度”的模式实现，避免并发下重复使用额度。
- 免费平台配额不等于商业 SLA，正式业务要留出模型切换开关与备用服务。

# 12. 获客与增长：不用烧钱买流量也能开始验证

## 12.1 三类免费流量

- 工具型 SEO：建立“某个术语是什么意思”“两种排盘口径有什么区别”“排盘输入如何核对”等高质量页面；页面要真正提供工具和解释，不做批量低质量 AI 页面。
- 短内容：用 30–60 秒解释一个术语、一个常见误区或如何核对排盘，结尾引导到免费工具；不要宣称必准、包发财、保证复合。
- 学习社区：发布开源的小型计算验证工具、排盘口径比较表、古籍术语卡；鼓励用户反馈错误并提供透明的修订记录。

## 12.2 冷启动路径

- 第 1 周：访谈 10 名目标用户，确认他们目前用什么工具、最常在哪一步浪费时间、愿意为哪种结果付费。
- 第 2 周：让 5–10 名用户试用最小流程，观察他们是否真的完成排盘、是否读取引用、是否保存报告。
- 第 3 周：只对一个明确价值点试售小额报告；清楚写清交付内容、价格、退款规则和工具性质。
- 第 4 周：复盘流量→开始排盘→完成报告→回访→付费的漏斗，决定继续做、修改定位或暂停。

## 12.3 关键指标

- 激活率：访客中完成一次排盘的比例。
- 报告完成率：点击 AI 解读后成功得到结构化报告的比例。
- 引用覆盖率：报告中可验证引用的关键解释比例。
- 复访率：7 日/30 日内再次使用的比例。
- 付费转化率和退款率：按真实用户行为统计，不用点赞和注册数代替收入验证。
- 单位贡献毛利：每份报告收入减去模型、支付和增量运维成本。
- 质量指标：已知样例盘面一致率、规则召回率、幻觉/无出处陈述比例、用户纠错率。

# 13. 测试计划与验收标准

## 13.1 排盘测试

- 建立人工核验的基准样例：普通日期、立春前后、节气交界、子时边界、时区转换、未知出生时间、闰月（支持后）。
- 每个样例记录输入、期望输出、所采用规则口径、来源与审校人。规则口径升级时必须运行全量回归。
- 采用两个独立来源交叉核验；若来源间口径不同，不要简单把差异视为程序错误，应记录差异原因并让用户选口径。

## 13.2 AI 测试

- 引用真实性：所有 citation_id 必须存在，并且被引用片段确实支持那句解释。
- 事实不变：模型输出不得修改排盘结果。
- 结构正确：百分之百通过 JSON Schema 或进入降级路径。
- 拒绝/安全测试：赌博/下注、医疗、法律、投资指令、恐吓话术、第三方隐私问题。
- 提示注入：知识片段或用户输入里出现“忽略系统提示”等内容，不得改变系统规则。
- 成本/时延：设置 P50/P95 延迟门槛，失败重试有上限。

## 13.3 MVP 验收清单

- 新用户能完成一次四柱排盘，并看到口径与警告。
- 基础盘面完全由确定性引擎返回；AI 无权修改 chart_facts。
- 刑冲合害规则可单独测试且附 rule_id。
- AI 报告有结构化章节和知识引用；无法引用时明确提示不足。
- 用户只能读取/删除自己的记录；分享链接有权限校验和撤销。
- 额度扣减幂等；支付回调重复发送不会重复发放权益。
- 管理员发布新技能前必须完成评测和审核记录。
- 隐私政策、用户协议、AI 使用说明、价格/退款说明和投诉入口可访问。

# 14. 部署与安全

## 14.1 最小生产部署

互联网 → Nginx HTTPS → FastAPI 容器 → MySQL 内网；MySQL 不直接开放公网端口。密钥用部署环境 Secret/安全配置注入；生产和测试环境数据库必须分开。

## 14.2 上线清单

- 强制 HTTPS、配置安全响应头、限制上传文件类型/大小、限速登录和生成报告接口。
- 使用 Argon2id 或 bcrypt 哈希密码；登录/验证码有防爆破策略；高权限后台启用多因素认证（如可用）。
- 数据库每日备份并定期做恢复演练；备份加密并限制权限。
- 日志脱敏：隐藏 API Key、访问令牌、生日详细输入和用户完整问题；按业务需要保存最少字段。
- 错误响应不要泄露堆栈、SQL、路径或模型供应商密钥。
- 设置模型预算、Token 上限、并发限流和服务熔断；记录 provider 健康状态，支持紧急关闭 AI。
- 支付采用可靠服务商的官方流程；服务器仅处理已校验的服务端回调，不相信前端“支付成功”参数。

# 15. 合规与平台政策检查（上线前必须完成）

本章是工程检查清单，不构成法律意见。你的运营地区、网站功能、收费方式、用户对象和模型调用方式会影响具体义务。尤其面向中国大陆公众收费上线前，应向属地通信管理、网信部门或专业律师确认适用规则，不要仅凭网上文章判断。

## 15.1 网站备案和经营许可

《互联网信息服务管理办法》区分经营性与非经营性互联网信息服务，并规定经营性服务许可、非经营性服务备案等要求；收费的网站服务不能简单假定只需普通 ICP 备案。先明确经营主体、网站服务类型、收费内容和部署地，再向属地通信管理部门核实适用的备案/许可要求。参考官方文本：https://sdca.miit.gov.cn/zwgk/fgbz/art/2026/art_fea940f81f1d423e87101adf147ab979.html

## 15.2 生成式 AI 服务备案/登记与标识

《生成式人工智能服务管理暂行办法》适用于向境内公众提供相应生成式 AI 服务的情形；网信办 2026 年 9 月公告说明，直接调用已备案模型能力的部分应用/功能存在属地登记流程，并要求已上线应用在显著位置或产品详情页公示所使用服务的模型名称和备案号/上线编号（具体适用情形以主管部门要求为准）。在决定模型供应商和上线地区前，先核实是否适用备案/登记。官方参考：https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm ；https://www.cac.gov.cn/2026-09/14/c_1791136833136332.htm

《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行，涵盖符合规定情形的生成文本、图片、音频、视频等服务。需要据具体服务场景确认显式/隐式标识要求，并为复制、下载、导出等功能设计相应标识处理。官方参考：https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm

## 15.3 个人信息保护

出生日期、时间、出生地、保存的命盘与用户账号关联时可能构成个人信息。按照《个人信息保护法》的最小必要、目的明确、透明告知等原则，默认匿名排盘优先；保存/AI 解读前清晰解释处理目的与数据项；允许查询、更正、导出和删除；设定保存期限和撤回同意流程；不要把用户资料默认用于训练。官方参考：https://www.miit.gov.cn/jgsj/zfs/fl/art/2022/art_515a4b20c12f430eab54bb4f56d89f56.html

## 15.4 内容与宣传边界

- 将产品定位成传统文化学习、资料整理与娱乐参考，不宣称有科学验证的命运预测能力。
- 避免“必准、百分百、保证发财、疾病必然、灾祸不可避免”等绝对化或恐吓式内容。
- 不设计赌博、下注、彩票、交易买卖或其他高风险决策的结果推荐。
- 对涉及医疗、法律、金融问题的输入，明确不作为专业意见，并引导用户以现实信息和合格专业服务为准。
- 设置投诉举报入口、内容审核、用户协议和退款规则；根据实际服务类型确认需要的许可证、备案和特别监管要求。

# 16. 开发排期与任务拆分

以下按开发顺序拆分，不把时间承诺当成结果保证。建议先用一个里程碑完成闭环，再扩展术数数量。

- M0 产品验证：竞品走查、10 位目标用户访谈、确认一个核心付费场景、明确数据与内容边界。
- M1 基础网站：Vue 页面框架、FastAPI、MySQL 迁移、登录/访客模式、部署环境和基本日志。
- M2 四柱引擎：选定排盘口径、结构化输出、边界测试、刑冲合害规则引擎。
- M3 AI 解释：知识条目/出处、RAG、模型适配器、JSON 输出与引用校验。
- M4 用户资产：命盘保存、笔记、报告历史、删除/导出。
- M5 商业化：免费额度、单次报告、用量账本、订单与支付接入（完成合规核验后）。
- M6 质量发布：安全测试、恢复演练、隐私政策/协议、真实用户试用和修复。
- M7 扩展：达到使用与留存目标后，再做紫微、六爻、奇门中的下一个模块。

每个里程碑完成定义：功能可演示、自动测试通过、接口文档更新、失败路径可见、无密钥泄露、数据可删除/备份、版本可回滚。

# 17. 运营后台与技能发布流程

后台最低限度包含：知识来源登记、知识片段审核、技能版本管理、评测集执行、模型调用监控、用户问题反馈、订单/额度检索、数据删除请求处理。

技能发布流程：编辑草稿 → 自动 schema 校验 → 规则单元测试 → AI 回归评测 → 版权/引用检查 → 人工审核 → 生成 checksum → 发布为新版本 → 灰度抽样 → 监控幻觉/投诉率 → 必要时回滚。生产中禁止直接覆盖旧版本。

可设置“自动构建、自动测试、人工批准发布”。这是真正适合个人开发者的自动化：节省重复工作，同时保证知识库不会被未经审核的生成内容悄悄改坏。

# 19. 风险清单与应对

- 排盘不一致：公开排盘口径差异会引发用户质疑。应对：明确口径、保存版本、提供差异说明和参考样例。
- AI 幻觉：模型会编造古籍章节或把不存在的规则说得很肯定。应对：引用必须来自检索结果，服务端验证引用 ID，低依据时降级。
- 免费额度失效：平台更改配额或封禁商用。应对：确认条款、做模型适配层、缓存基础结果、设置降级模式。
- 获客不足：网站功能多但没有自然流量。应对：先验证一类用户的具体工作流，持续做高质量工具和说明内容。
- 隐私风险：出生资料和问题记录泄露。应对：最小收集、默认私密、加密备份、访问控制、删除机制和日志脱敏。
- 合规风险：收费、AI 功能、内容发布、经营主体可能触发不同要求。应对：上线前向属地主管部门确认，不把免责声明当作合规替代品。
- 知识版权问题：古籍整理版、课程、网站内容可能有权利限制。应对：保存许可元数据，优先授权/公版材料，设下架流程。

# 20. 上线前决策清单

- 是否已确定首版只做一个模块，而不是同时承诺所有术数？
- 排盘口径是否写明，并有独立校验样例？
- 模型是否通过 API Adapter 接入，密钥没有暴露给前端？
- 知识库内容是否有来源、许可证状态、审核状态与版本？
- AI 是否只解释结构化盘面，且引用必须可验证？
- MySQL 是否有用户隔离、备份、删除和迁移方案？
- 收费/免费额度/退款/续费是否清楚且经合规核验？
- 隐私政策、用户协议、AI 提示、投诉入口是否完整？
- 对中国大陆公开上线，是否已向属地部门核实 ICP/经营许可与生成式 AI 的适用要求？
- 是否找真实用户完成过任务，并拿到至少一个有依据的付费信号？
