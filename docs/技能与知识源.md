# 技能与知识源

> 三个概念经常被混着叫「知识」：**任务包**、**知识库**、**技能文件**。
> 它们的作用、位置、能否被引用都不一样，这一页把边界写死。

---

## 1. 一张表看懂

| 概念 | 位置 | 何时注入 | 能否作为引用 |
|---|---|---|---|
| **任务包** | `backend/app/domains/skills/packages/*.json` + `reporting/prompts/*.txt` | 每次生成报告都按 domain/深度选中一份 | 否 |
| **技能文件** | `backend/skills/**/*.md` | **每次 AI 调用前必读**（全局 + 领域），卡片按触发词追加 | 否，只影响叙述顺序与自查 |
| **知识库** | MySQL `knowledge_chunks`（源 `docs/知识源/*.md`，`approved`） | 检索命中才注入 | **是**，`citations` 只认 `chunk_id` |

一句话：任务包决定「用哪套模板」，技能文件决定「按什么顺序想」，知识库决定「能引用哪句原文」。

## 2. 技能文件目录

```
backend/skills/
├── SKILL.md                 # 全局必读：身份、输出契约、红线
├── _draft/                  # 蒸馏草稿：不加载，人工复核后转正
├── bench/SKILL.md           # 评测专用：必须作答、先定时间再筛选项
├── bazi/
│   ├── SKILL.md             # 领域必读：看盘顺序、大运流年、常见错误
│   └── cards/
│       └── bazi.relations.order.v1.md
├── ziwei/SKILL.md + cards/
├── liuyao/SKILL.md + cards/
└── qimen/SKILL.md + cards/
```

### front-matter 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一标识，写进 `validation.skills_used` |
| `domain` | 是 | `common` / `bazi` / `ziwei` / `liuyao` / `qimen` |
| `title` | 是 | 面板与日志里显示的名字 |
| `status` | 是 | 只有 `approved` 会加载；`draft` / `deprecated` 一律跳过 |
| `always` | 否 | `true` = 每次注入；领域 `SKILL.md` 无论写不写都按 `true` 处理 |
| `triggers` | 否 | `always: false` 时按命中数排序 |
| `priority` | 否 | 同命中数时排序 |
| `max_chars` | 否 | 单文件上限，超出截断并标 `…[截断]` |
| `version` / `source` / `updated` | 否 | 审计用 |

## 3. 加载与注入

实现：`backend/app/domains/skills/skillfile.py`

1. 全局 `SKILL.md` → 领域 `SKILL.md` → 卡片（触发词命中数 → priority）
2. 总预算 **4000 字符**，填满即停；单文件按 `max_chars` 截断
3. `_draft/` 不递归、跨 domain 不加载、非 `approved` 不加载
4. 提示词顺序固定：

```
system_v2
user:
  【必读技能】全局 + 领域
  【参考经验】命中卡片（可以为空）
  盘面事实 / 规则白名单 / 知识片段
  【输出契约】
```

三个入口共用同一份实现：

| 入口 | 文件 |
|---|---|
| 报告 | `app/domains/reporting/service.py::build_user_prompt` |
| 追问 | `app/domains/reporting/followup.py::_build_prompt` |
| 题库评测 | `scripts/bench_eval.py::build_prompt` |

每次调用实际用到的卡片 id 会写进 `validation.skills_used`（报告与追问）或评测记录的 `skills` 字段，便于做消融（`bench_eval --no-skills`）。

### 两种 profile

产品语气与考试语气是两件事，混用会让模型拒答：

| profile | 读哪些文件 | 用在 |
|---|---|---|
| `product`（默认） | 全局 `SKILL.md` + 领域 `SKILL.md` + 卡片 | 报告、追问 |
| `bench` | `skills/bench/SKILL.md` + 同领域卡片 | 题库评测 |

原因：产品要求「不断吉凶、不给应期」，而 MingLi-Bench 问的是「哪年结婚」；
拿产品人设去答题，模型会回避或拒答，测出来的是人设而不是判断力。
`skills/bench/SKILL.md` 只保留三条：必须选一项、先定时间再筛选项、盘面事实优先。

## 4. 蒸馏与转正

```bash
cd backend
# 1) 在 train 集上挖错题（test 只测量，不参与取样）
python -m scripts.bench_eval --dataset mingli_bench \
    --file data/bench/MingLi-Bench/train.jsonl \
    --attempts data/bench/train_attempts.jsonl --tag round2-train
python -m scripts.bench_stats --attempts data/bench/train_attempts.jsonl --min-wrong 2

# 2) 生成草稿（只写 backend/skills/_draft/）
python -m scripts.distill_skills --attempts data/bench/train_attempts.jsonl --min-wrong 2

# 3) 人工复核：改 status: approved、去掉 id 里的 draft.、移到 <domain>/cards/
#    更关键的是把它合并进 <domain>/SKILL.md，而不是堆一堆碎片

# 4) 测 delta
python -m scripts.distill_round --round 3 --no-distill --model minimax-m3.1-flash
```

转正红线：

- 卡片只写「先看什么、再看什么、最容易错在哪」，不写具体命理结论；
- 不编造规则、不引用页码、不写吉凶；
- 每轮只动 1–2 张卡，否则无法归因；
- `_draft/` 里即使 `status: approved` 也不会被加载（目录本身被排除）。

## 5. 首轮实测（2026-10-25，MingLi-Bench 留出集）

| 配置 | 准确率 | 说明 |
|---|---|---|
| 无技能基线 | 38.5%（15/39） | 只有盘面事实 + 知识片段 |
| 产品 profile | 0.0%（子集 10 题） | 模型按「不做断语」回避，明显下降 |
| bench profile v1 | 33.3%（13/39） | 加上「必须作答 / 先定时间 / 类目经验」 |
| bench profile v2 | 33.3%（13/39） | 精简为 4 条，只留必须作答与时间筛选 |

结论（写下来避免自欺）：

1. **产品人设不能直接拿来答题**：一问「哪年结婚」就拒答，准确率归零；`bench` profile 是必需的，
   不是「多此一举」。
2. **精简没有带来提升**：v1 与 v2 同为 33.3%，说明瓶颈不在文案长短，而在模型的结构推理能力。
3. **39 题的标准误约 ±7.5pp**，33.3% 与 38.5% 相差不到一个标准误，不能断言「技能有害」。
4. 下一轮应扩大到 train 121 题、固定 temperature/seed，并先补「卡有/无」的 4 单元格对照，再决定是否继续写卡。
5. 留出集已被多轮使用，后续应以新的命例切分重做一次干净测量。

## 6. 知识源入库

```bash
# 本地开发（一次性审核写入）
python -m app.domains.knowledge.ingest --domain bazi --dir docs/知识源 --approve
python -m app.domains.knowledge.ingest --domain ziwei --dir docs/知识源/ziwei --approve

# 线上必须走审核脚本
python -m scripts.admin approve --id <id>
```

知识片段进入 `knowledge_chunks` 后才可能被检索；检索只返回 `approved`，未审核内容不会出现在任何 prompt 里。

## 7. 外部技能包：taibu（太卜）

外部项目：https://github.com/hhszzzz/taibu，本地路径 D:/瞎玩/taibu。
许可证 **AGPL-3.0**（另附 licenses/pi.LICENSE），因此：

- **只读、不复制**：运行期按路径读它的 Markdown，不把内容拷进本仓库，也不提交到 git；
- **不执行它的引擎**：对方打包了 11MB 的 Node bundle，本项目用自己的 Python 引擎算盘，
  盘面事实只有一个来源。

### 配置

`env
# backend/.env
SKILLS_EXTRA_DIRS=D:/瞎玩/taibu/skills/taibu-divination
SKILLS_EXTERNAL_IN_PRODUCT=false
`

### 加载什么

| 文件 | 是否注入 | 说明 |
|---|---|---|
| 	aibu-divination/SKILL.md | 否 | 是对方 CLI 的工具路由表（
ode taibu.mjs），本项目不能执行，注入只会占预算 |
| interpretation/bazi.md | 是（bench 默认） | 按文件名映射到 azi |
| interpretation/ziwei.md | 是（bench 默认） | 映射到 ziwei |
| interpretation/liuyao.md | 是（bench 默认） | 映射到 liuyao |
| interpretation/qimen.md | 是（bench 默认） | 映射到 qimen |
| 
eferences/*.md | 否 | 工具参数表，与解读无关 |

注入位置在 prompt 的「【外部技能包】」段，前面固定加上一句：

> 仅作方法参考；其中的吉凶断语与绝对化表述不得照搬，与本项目红线冲突时以本项目为准，
> 也不得写进 citations。

### 为什么产品侧默认关

	aibu 的解读指引要求「给出时间范围、吉凶属性与影响程度」，这与本项目的红线
（不断吉凶、不给应期）直接冲突。默认只在**题库评测**里启用，用于吸收它的分析框架；
报告与追问保持本站口径。确需在报告侧试用时，把 SKILLS_EXTERNAL_IN_PRODUCT 打开，
但要接受「外部包可能诱导出吉凶表述」的风险。

### 触发与预算

- 触发词按体系固定：八字含「四柱/日主/十神/大运/流年/命盘」，紫微含「宫位/四化/大限/小限」…
- 单文件上限 1600 字符，与本站技能共用 4000 字符总预算；
- 未配置 SKILLS_EXTRA_DIRS 时完全不加载，测试也不会依赖 taibu 是否存在。
